1 · What Vigil is (and is not)

Vigil is a hybrid: a deterministic statistical-plus-rules risk engine, an LLM-assisted investigation layer, and a human decision log with an append-only audit trail.

LayerOwnsHow
Risk enginethe 0–100 score and the recommended action 6 signal detectors → grouped noisy-OR fusion → leave-one-out attribution → 3 hard rules that impose score floors → a fixed action policy. Hand-set weights. Deterministic.
AI investigationthe narrative, findings and a second opinion Gemini gemini-3.6-flash agentic loop over 5 read-only tools, or a deterministic engine-only fallback. Every number it states is re-checked against the database.
Human analystthe decision Allow / Monitor / Step-up / Hold / Block, with a mandatory written reason on any override, recorded in the audit trail.

It is NOT:

  • a machine-learning model. There is no trained/loaded model anywhere — no sklearn, torch or tensorflow. numpy is used only for median / percentile / MAD. The score is arithmetic over constants.
  • a payment interceptor. There is no gateway. "Block" and the other actions write a Decision row and change the case status; Transaction.status never changes and no money is actually stopped.
  • connected to real data. 100% synthetic, generated locally. Ground-truth attack tags are used only for the detection-rate metric and are hidden from the engine and the AI.

2 · The problem it solves

A fraud analyst faces a queue of flagged payments and must decide, in seconds each, whether to let one through or stop it. The evidence is scattered across transaction history, device graphs and auth logs. Vigil does that assembly up front and hands over a decision-ready case: the specific warning signs, a score with a transparent breakdown, a recommended action, and — when available — an independent AI second opinion with every figure verified. The analyst still decides; Vigil makes the decision fast and auditable.

3 · How Vigil works

PAYMENT ↓ RISK SIGNALS 6 checks vs THIS customer's own history: amount, velocity, failed logins, new device, location, time-of-day ↓ RISK ANALYSIS grouped noisy-OR fusion (overlapping evidence not double-counted) + 3 hard rules that set a minimum score (a "floor") ↓ RISK SCORE 0-100 -> LOW <35 | MEDIUM 35-61 | HIGH 62-81 | CRITICAL >=82 ↓ RECOMMENDATION fixed policy: band + rules -> Allow / Monitor / Step-up / Hold / Block ↓ AI INVESTIGATION (optional) Gemini reads the case, writes evidence-cited findings, offers a second opinion; every number re-verified against the DB ↓ HUMAN DECISION analyst picks an action; override needs a written reason; audit trail

A case is opened automatically only when the score reaches 60. Lower-risk scenarios still produce a full score and recommendation — they just don't create an alert.

6 · How the risk score is calculated

  1. Signals. Each of 6 detectors returns a normalized severity in 0–1 and has a fixed weight. Its contribution is weight × normalized.
  2. Fusion (grouped noisy-OR). Correlated detectors share a group (velocity+auth, device+geo). Within a group and then across groups: p = 1 − Π(1 − contribution). base_score = round(100 × p). This bounds the score to 0–100 without clipping and stops "new device + new city" counting twice.
  3. Attribution (leave-one-out). Each signal's share = how much the fused score drops if you remove it, normalised so the shares sum to ~100%. Shown in the UI as "% of base".
  4. Rules. 3 deterministic rules each impose a score floor. The governing floor is the highest one that fired.
  5. Final score = max(base_score, governing floor), clamped 0–100. A rule can only raise the score to its floor, never lower it.
  6. Band from the final score; action from a fixed policy over (band, rules, amount, KYC).

The UI's "Why this score?" panel is built entirely from these numbers:

The "points" are the engine's exact leave-one-out attribution of the fused score multiplied by the base. They are an honest decomposition, not additive weights invented for the slide. Same DB state → same numbers, every time.

The 3 rules (score floors)

9 · What happens after each click (technically)

  • Run scenario → POST /api/simulate/scenario → inject_scenario() builds transactions + auth events, scores them with the engine, opens a case iff score ≥ 60. All rows persisted to SQLite.
  • Run AI investigation → POST /api/cases/<id>/investigate → creates an AgentRun; Gemini tool-loop (or fallback); writes an evidence ledger, then findings with VERIFIED / UNVERIFIED / REFUTED tags after the grounding check; case status → REVIEW_REQUIRED.
  • An analyst action + Confirm → POST /api/cases/<id>/decision → apply_decision() inserts a Decision row, sets Case.status (BLOCK/HOLD_FOR_REVIEW → BLOCKED; the other three → APPROVED), sets closed_at, and appends an analyst_decision audit entry. If the action differs from the engine's recommendation and no reason is given → HTTP 422.
Be upfront about this limit: the five actions differ in what is recorded (final action, reason, audit entry) and in the resulting case status, but there is no payment gateway — Transaction.status never changes and nothing is actually blocked or held. Vigil is decision support and an audit record, not an enforcement point.

10 · Role of the risk engine

Owns the score and the binding recommended action. Pure, deterministic arithmetic — 6 weighted signal detectors, grouped noisy-OR fusion, leave-one-out attribution, 3 rule floors, a fixed policy matrix. No ML, no randomness at scoring time, fully reproducible. Runs in single-digit milliseconds. The AI cannot change any of it.

11 · Role of Gemini / AI

Runs only when the analyst clicks Run AI investigation. Model: gemini-3.6-flash, driven through an agentic loop over 5 read-only tools (risk assessment, customer profile, transaction history, auth events, device/IP graph). It produces:

  • a plain-language investigation summary and behavioural comparison;
  • findings — each quantitative one names a metric the backend then re-computes from the database (±1% tolerance) and tags VERIFIED / UNVERIFIED / REFUTED;
  • a qualitative risk view (LOW–CRITICAL) — not a 0–100 number; the schema has no score field;
  • a second opinion: agree, or dissent with a reason (e.g. "this is a ring — block the device, don't just hold one payment");
  • an advisory recommended action.

Gemini never computes the score, never decides, and has no tool that can change anything. If it errors or hits quota, Vigil automatically falls back to a deterministic engine-only investigation, clearly badged (see §17).

12 · Role of the human analyst

The only actor who can resolve a case. Picks Allow / Monitor / Step-up / Hold / Block. Choosing anything other than Vigil's recommendation requires a written reason, stored with the analyst's identity and timestamp in the append-only audit trail. The analyst can agree with the engine, agree with the AI's dissent, or overrule both.

13 · Technical architecture

Frontend backend/static/index.html (single file, Alpine.js + Tailwind, no build) | fetch() API FastAPI routers backend/api/*.py | Engine backend/risk/ signals.py -> fusion.py (noisy-OR) -> rules.py (floors) -> policy.py | AI backend/agent/runner.py -> Gemini agentic loop | fallback.py (deterministic) | tools.py (5 read-only) ledger validator.py (re-verify every number) v Store SQLAlchemy -> SQLite (customers, transactions, auth_events, risk_assessments, risk_signals, cases, case_evidence, agent_runs, agent_findings, decisions, audit_log)
Deployment
One FastAPI process serves the API and the SPA on the same origin. Free-tier Render blueprint in render.yaml.
Data
Synthetic, generated by backend/seed.py with random.Random(42). ~1,080 transactions across 12 customers, 90 days of history each.
AI safety
Read-only tools; no score field in the output schema; grounding validator re-computes every claim; failed claims shown with a warning, never dropped.
Fallback
No GEMINI_API_KEY or any Gemini error → deterministic engine-only investigation, mode="fallback", badged in the UI.
Persistence caveat
SQLite on Render is ephemeral (resets on redeploy). Within a session it is real persistence; Reset demo re-seeds.
Full-detail view: 5-layer score calculation, AI mode/model/tool-calls/latency, grounding verdict, findings with verification tags, evidence ledger, per-signal bars, timeline, audit trail.

14 · 30-second explanation

"Fraud analysts drown in alerts, and each one is a fast human judgement call. Vigil does the investigation for them. A deterministic engine scores every payment 0–100 against that customer's own behaviour and shows exactly which signals drove the score. For risky ones, an AI agent reads the case and writes an evidence-backed second opinion — and every number it states is re-checked against the database. Then a human analyst decides: allow, verify, hold or block. The AI never scores and never acts; the engine never decides; the human is always in control, and every decision is in an audit trail."

16 · Likely judge questions + answers

QuestionAnswer
Is this machine learning?No. The score is deterministic arithmetic over hand-set weights and rules. No trained model. The only "AI" is Gemini in the optional investigation step, and it never scores.
Does the AI decide or block anything?No. It has read-only tools and no score field. It writes an opinion. A human makes the binding decision.
What if the AI hallucinates a number?Every quantitative claim is re-computed from the database (±1%). It's tagged VERIFIED / UNVERIFIED / REFUTED and a grounding verdict is shown. Failed claims are surfaced, not hidden.
Why did this get 95/100?Point at "Why this score?": the per-signal breakdown that sums to the base, plus the rule floors. It's the engine's own attribution, reproducible.
Why noisy-OR instead of adding weights?It stays in 0–1 without clipping, is monotonic, and stops correlated signals (new device + new city) from double-counting. Exact attribution falls out of it.
Does it over-alert?Run the Normal scenario: 0/100, no case. Detection rate on the seeded known-fraud set is ~84–88% at HIGH+ while ~85%+ of all traffic stays LOW.
If the analyst disagrees with Vigil?They pick any action; a differing choice requires a written reason, stored in the audit trail with identity and timestamp.
Is the data real?No — 100% synthetic, generated locally. Attack labels are used only for the detection metric and are hidden from the engine and AI.
Does "Block" actually stop a payment?Honest answer: no. There's no gateway in this demo. It records the decision and changes the case status. The engine, the investigation and the audit trail are the real parts.
How fast?Engine: single-digit milliseconds. The optional live AI investigation: ~1–3 minutes; it's off the critical path.

19 · What to say to the judges / What not to claim

WHAT I SHOULD SAY TO THE JUDGES

"Vigil is an AI-assisted risk-investigation tool for payment fraud analysts. It has three parts with clean boundaries.

A deterministic risk engine scores every payment 0 to 100 against that customer's own history — six weighted signals (amount, velocity, failed logins, new device, location, time), combined with a noisy-OR model so overlapping evidence isn't double-counted, plus three hard rules like impossible travel that set a minimum score. The score is a fixed formula: same inputs, same number, and the UI shows the exact per-signal breakdown.

An AI investigation agent — Gemini — runs on demand for risky cases. It reads the case with read-only tools and writes an evidence-cited summary and a second opinion. Crucially, every number it states is re-computed against the database and marked verified or not. It never produces the score and it cannot take an action. If it's unavailable, a deterministic fallback fills in.

A human analyst makes the final decision — allow, verify, hold, or block — and any departure from Vigil's recommendation needs a written reason. Everything lands in an append-only audit trail.

The data here is synthetic. What's real and working is the scoring, the explanation, the grounded AI investigation, and the decision-and-audit workflow — and you can see the engine respond differently to a normal payment, a mildly odd one, and a full account-takeover."

WHAT NOT TO CLAIM

  • Don't call it machine learning or say it "learns" / "was trained". It's rules + statistics with fixed weights.
  • Don't say Gemini detects fraud or produces the risk score. It investigates and gives a second opinion; the schema has no score field.
  • Don't say Vigil blocks / holds / stops payments. There is no payment gateway. It records a decision and changes a case's status; the transaction itself is untouched.
  • Don't present the detection rate as real-world performance. It's measured on the seeded synthetic attack set.
  • Don't imply the data is real or Razorpay production data. It is generated locally.
  • Don't claim real-time streaming / scale numbers. It's a single FastAPI process on SQLite; the engine is fast but this is a demo, not a benchmarked system.
  • Don't say the AI "decides when to escalate". The policy that maps score+rules to an action is a fixed if/elif matrix in policy.py.
  • Don't over-state the fallback dissent. In engine-only mode the "disagreement" is one fixed rule (ring detected → block the device), not a model judgement — the UI labels it as such.
